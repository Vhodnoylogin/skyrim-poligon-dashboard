# Diagnostic pre-execution recovery

## Retaining the installed subject under renewed owner authority

`diagnostic-preparation-renew REVIEW.json` renews only a never-frozen technical
preparation after explicit current owner authorization. The queued subject,
installed files, slot/acknowledgement, retained qualification hold and historical
starts stay unchanged. The old request, cycle policy and source are captured in
an immutable certificate and audit event; no game or installation is performed.
New review fields are defined by `diagnostic_preparation_renewal.py`.

Certificate files use immutable content-addressed names. A refused transaction
may leave an unregistered capture, which is preserved as evidence. A later retry
captures fresh observations without overwriting or adopting that orphan. Only a
committed audit event registers a renewal; successful duplicate requests return
that original registration. Freeze and execute remain separate existing commands.

This cleanup-only protocol settles a never-frozen/consumed technical preparation.
It grants no game start, source overlay, qualification or new test authority.
The original queued subject's entire row, raw order and history remain unchanged;
no mod build/order, subject progress, cycle reset, result packet or notification
is created. Expired test authority is historical owned-installation provenance
for cleanup only. Future same-subject preparation needs a separately reviewed
generation binding and current owner bounds, outside this protocol.

Use the independent reviewed recovery source tree, without changing old917 files.
Its adjacent `legacy-diagnostic-917-source.json` MUST be included in every copy
and source export. The hashed manifest records our own exact published41Python
producer files, repository/commit and source-archive reacquisition hash. It is
source metadata; third-party tools/binaries are not bundled or committed.

`diagnostic-recovery-inspect ID` provides immutable review hashes without cleanup
or native approval. `diagnostic-recovery-reserve REVIEW.json` validates the exact
old request, source manifest/physical source, original file-ACK/grant/event graph,
queued order, true fresh preimages and sole owned installation reservation. It
rejects every platform/attempt/session/runtime/worker or unknown dispatch trace.
Under the existing native mutex and SQL transaction, it records immutable source
bytes/snapshots/proofs and changes only the technical diagnostic to `restoring`.
The queued job, reserved slot and Q1 failure hold remain. Old freeze/execute
guards refuse this state. The API does not perform restoration or invoke actors.

The separately approved origin-owned native UI/helper must archive and verify
all13owned current postimages:10published payload files, native meta.ini and the
two copied download records. It then restores their proven prior absence and
ONLY the fresh native modlist backup. Other nine profile preimages, other profile
modlists and unrelated providers stay exact. No stale old-plan plugins/loadorder
restoration or copying an INI over live MO2 is permitted. Every directory/reparse
entry and other profile reference is checked before the global mod can be removed.

`diagnostic-recovery-complete REVIEW.json` verifies the scoped13-file archive,
actual absent owned delta, fresh modlist/profile bytes, source/proof pins and
complete current native idle observations. ManagedINI evidence must be an
immutable copied snapshot under this recovery's evidence folder. The existing
strict10-key GUI-only parser permits reviewed persistence differences; all other
INI values remain exact. Completion records raw process inventory, checked old
owner identities and runtime-state pins without new process probes.

The completion review also pins an external typed native-restoration receipt:
same recovery/reserved review/origin/SE instance/profile, current PID+birth+path
of the real manager, no-game flag, archive/rollback targets, reviewed actor source
and evidence, and refreshed known-idle/absence/VFS readbacks. Seven game paths
must return original pinned providers/hashes. Only the exact three top-level
claw-build.json/README.md/README.ru.md paths may truthfully be absent or resolve
to another current provider; none may retain the removed mod root. This combines
physical postconditions with independently reviewed pinned UI/readback evidence;
it does not pretend filesystem observations alone prove native UI provenance.

After all captured pins are rechecked at the mutation boundary, completion changes
ONLY the old technical diagnostic to `recovered-unstarted` and its slot to
`released`. Old actual_starts remains NULL. Positive zero is scoped to this
recovery generation; global history remains unknown. Q1 hold and the ENTIRE
queued job/cycle remain unchanged. Audit uses recovery/slot identities, never
the subject ID. No callbacks, game, outbox item or automatic new preparation.

`diagnostic-recovery-show ID` reports cleanup-only state and verifies supported
historical completion. The recognizer binds immutable row/event/snapshot/source
and archive evidence, checks subject history through the completion boundary,
and does not demand old live provider/manager/source files remain unchanged
forever. Duplicate completion returns the same historical closed receipt;
duplicate reservation grants no new cleanup. Lost response, partial restoration
or failed proof retains `restoring`, its slot and barriers. No timeout infers zero.

## Current restoring-scope guard for the reviewed actor

Status/show output is not a validated current lease. The actor must hold the
existing SessionMutex across a child CLI call and the bounded action that
follows it. `diagnostic-recovery-guard QUERY.json` NEVER acquires that mutex;
calling it in a subprocess while its parent owns the lock must not deadlock.
Lock ownership is the reviewed caller's precondition, not a claim proved by this
API. The entrypoint opens only an EXISTING database in SQLite mode=ro/query_only,
before the normal constructor can create schema/witness rows. It creates nothing.

The exact query keys are schemaVersion=1, kind=diagnostic-preexecution-restoring-guard,
id, reservedReviewPin and stage. `pre-archive` requires all13owned postimages and
returns COPY-ONLY current scope; the actor independently copies/resumes its known
archive without overwriting unknown data. `partial` additionally REQUIRES archive
pin and all13archived members before any absence/removal is accepted. Remaining
source files may only retain their known hashes or be absent; known parent
directories, reparse guards and unrelated profile/provider pins stay enforced.
Source modlist bytes may be only the exact captured postimage, its ONE new-mod
enabled→disabled prefix change, or the exact fresh preimage. No newline/other
entry normalization is admitted. New reserve captures the exact postimage bytes;
there is no migration of an older registered recovery to this implementation.

Successful output kind validated-current-restoring-scope binds current record
hash, reserved review, implementation pins, allowed13postimages, fresh modlist
backup, factual stage proof and raw idle observations. newCleanupGranted and
launchGranted remain false; mutexOwnershipProvedByGuard is false. Failed,
completed, foreign, stale or changed records return no usable scope. The actor
must check exit status and all expected identity/pin fields immediately before
each bounded action and decode child JSON as UTF-8. No UI callback, private DB
access, source overlay, new deadline/cap or new preparation is provided.
